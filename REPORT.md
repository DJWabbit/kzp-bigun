# Звіт до лабораторної роботи №5

## 1. Тема, номер і варіант

- **Тема:** «Параметризоване сховище, винятки й CSV-експорт у Java-проєкті».
- **Лабораторна робота:** №5 з дисципліни «Кросплатформні засоби програмування».
- **Варіант:** №4, предметна область «Склад автозапчастин»; клас запису `SparePartRecord`, ключ – артикул.
- **Рівень:** 2 (інженерний).
- **Операційна система:** Windows 11 Home.
- **Репозиторій:** https://github.com/DJWabbit/kzp-bigun, гілка `lab5`.

## 2. Мета роботи

Мета роботи – замінити пряме зберігання даних у списку на параметризоване сховище, додати власний виняток із ланцюгом причин, описати CSV-стовпці анотацією та реалізувати універсальний експортер, який читає метадані рефлексією. Дані записуються і читаються через `Path` та `Files` з явним UTF-8.

У результаті програма експортує деталі у CSV, відновлює їх і доводить рівність початкових та відновлених записів. Попередні режими та звіт не змінилися.

## 4. Repository<T>

Параметр `T` визначає тип записів, тому сховище працює з деталями, записами CSV і будь-яким іншим типом без приведень і raw types.

- `add` додає непорожній запис;
- `all` повертає незмінний знімок, на який не впливають подальші додавання;
- `find` приймає `Predicate<? super T>`, тобто умову для типу або його супертипу.

Лістинг 1 – пошук у сховищі:

```java
public List<T> find(Predicate<? super T> predicate) {
    Objects.requireNonNull(predicate, "Предикат не може бути null");
    return items.stream()
            .filter(predicate)
            .toList();
}
```

Сховище використовують `InventoryFileReader` для деталей і `CsvStorage` для відновлених записів.

## 5. Модель даних

Для CSV створено окремий плоский запис `SparePartRecord`. Анотувати `SparePart` недоцільно: його `equals` порівнює лише підтип і артикул, тому round-trip не виявив би втрату ціни чи назви. `SparePartRecord` є record, і його `equals` та `hashCode` охоплюють усі поля.

| Поле | Тип | Стовпець |
|---|---|---|
| article | String | артикул |
| manufacturer | String | виробник |
| name | String | назва |
| price | double | ціна |
| quantity | int | кількість |

Інваріанти перевіряє той самий метод, що й у `SparePart`, тому правила не дублюються. `from` створює запис із деталі, `toPart` – деталь із запису. Вид деталі не зберігається: `PartKind` відновлює підтип за артикулом.

Лістинг 2 – оголошення запису:

```java
public record SparePartRecord(
        @CsvColumn("артикул") String article,
        @CsvColumn("назва") String name,
        @CsvColumn("кількість") int quantity,
        @CsvColumn("ціна") double price,
        @CsvColumn("виробник") String manufacturer) {
```

## 6. @CsvColumn

Анотація має `@Retention(RUNTIME)`, тому доступна рефлексії під час виконання, `@Target(FIELD)` і єдиний елемент `String value()` з назвою стовпця. На компонентах record вона потрапляє на відповідні поля. Анотація лише описує стовпець, а порядок визначає експортер: поля сортуються за Java-іменами.

Лістинг 3 – анотація:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface CsvColumn {
```

## 7. Рефлексивний експортер

`CsvExporter` не знає предметних класів. Він проходить клас і його базові класи до `Object`, залишає нестатичні поля з `@CsvColumn`, сортує їх за іменем і відкриває доступ через `trySetAccessible`. Клас передається окремо, тому заголовок створюється й для порожнього списку.

Клас без анотованих полів, однакові назви стовпців або заборонений доступ дають `DataStorageException`. Відсутнє значення стає порожнім полем. У тестах експортовано книжки та ієрархію тварин, щоб довести незалежність від деталей.

Лістинг 4 – пошук анотованих полів:

```java
List<Field> fields = Stream.<Class<?>>iterate(type, Objects::nonNull, Class::getSuperclass)
        .flatMap(level -> Arrays.stream(level.getDeclaredFields()))
        .filter(field -> field.isAnnotationPresent(CsvColumn.class))
        .filter(field -> !Modifier.isStatic(field.getModifiers()))
        .sorted(Comparator.comparing(Field::getName)
                .thenComparing(field -> field.getDeclaringClass().getName()))
        .toList();
```

Лістинг 5 – екранування:

```java
boolean special = value.indexOf(SEPARATOR) >= 0 || value.indexOf('"') >= 0
        || value.indexOf('\n') >= 0 || value.indexOf('\r') >= 0;
return special ? '"' + value.replace("\"", "\"\"") + '"' : value;
```

## 8. Формат CSV

Кодування – UTF-8, роздільник – кома, кінець рядка – `\n`; читання приймає також `\r\n`. Поле з комою, лапкою або перенесенням рядка береться в лапки, внутрішня лапка подвоюється. Ціна записується через `Double.toString`, бо два знаки після крапки втрачали б точність.

Заголовок:

```text
артикул,виробник,назва,ціна,кількість
```

Вміст `data/stock.csv`:

```text
артикул,виробник,назва,ціна,кількість
BRK-001,АвтоПостач,Гальмівні колодки,1250.5,12
FLT-014-R,Мотор-Сервіс,"Фільтр, масляний",320.0,25
SPK-210,Деталь+,"Свічка ""Іридій""",185.75,40
TIM-008,АвтоПостач,"Ремінь ГРМ
комплект",2100.0,7
OIL-101-R,"Мотор-Сервіс, Львів",Олива моторна,780.0,10
AMT-330,Деталь+,Амортизатор,2100.0,4
```

Файл має 8 фізичних рядків і 6 записів. `data/stock-invalid.csv` містить хибне число, `data/stock-empty.csv` – лише заголовок.

## 9. Імпорт і round-trip

1. `CsvStorage.read` читає весь файл через `Files.readString` з UTF-8.
2. `CsvDocumentParser` розбирає документ машиною станів, тому перенесення в лапках не розриває запис.
3. Заголовок порівнюється з очікуваним.
4. `SparePartRecord.fromFields` відновлює кожен запис; текст не обрізається.
5. Початковий і відновлений списки порівнюються через `equals`.

Вивід `--export` для `data/input.csv` та `--import data/stock.csv`:

```text
Експорт: записів 4
Round-trip: так
Імпорт: записів 6
- BRK-001 (оригінальна)
- FLT-014-R (замінник)
- SPK-210 (оригінальна)
- TIM-008 (оригінальна)
- OIL-101-R (замінник)
- AMT-330 (оригінальна)
```

## 10. Помилки

| Рівень | Повідомлення | cause і перевірка |
|---|---|---|
| Модель | Запис 2: ціна та кількість не можуть бути від'ємними | `IllegalArgumentException`; `reportsWrongValuesOfModel` |
| Формат | Запис 2: очікується 5 полів, отримано 4 | `DataStorageException`; `reportsWrongFieldCount` |
| Формат | Запис 2: лапки не закрито | без cause; `reportsBrokenQuotes` |
| Формат | Очікується заголовок CSV: … | без cause; `reportsWrongOrMissingHeader` |
| Значення | Запис 3: ціна та кількість мають бути числами | `NumberFormatException`; `reportsWrongNumberWithRecordNumberAndCause` |
| Файл | Не вдалося прочитати CSV … (NoSuchFileException) | `IOException`; `reportsFileErrorsWithCause` |
| Рефлексія | Клас … не має полів із @CsvColumn | без cause; `rejectsClassWithoutSuitableColumns` |

Для помилок моделі та значення початкова причина лежить у другій ланці ланцюга: зовнішній виняток додає номер запису. Номер рахується разом із заголовком. Порожній файл є помилкою заголовка, а файл лише із заголовком – коректним порожнім набором. Порожніх блоків `catch` немає.

Лістинг 6 – збереження причини файлової помилки:

```java
} catch (IOException exception) {
    throw new DataStorageException("Не вдалося прочитати CSV " + path, exception);
}
```

## 11. Тестування

Виконано 131 тест. Усі 80 тестів лабораторної роботи №4 збережено без змін, додано 51: 7 у `RepositoryTest`, 10 у `CsvExporterTest`, 12 у `CsvDocumentParserTest`, 15 у `CsvRoundTripTest` і 7 у `StorageReportTest`.

Позитивні випадки:

- додавання, знімок і пошук у сховищі;
- експорт довільного класу та успадкованих полів;
- round-trip шести записів і обох підтипів;
- `--export` і `--import`.

Граничні випадки:

- порожній список і файл лише із заголовком;
- кома, лапки, `\n`, `\r\n`, пробіли та порожній текст;
- точні значення `double`, найбільше `int`, символи за межами кирилиці;
- коротший експорт поверх довшого.

Негативні випадки:

- хибні заголовок, кількість полів і число;
- незакриті лапки та символи після лапок;
- відсутній файл, каталог замість файла, хибне UTF-8;
- клас без анотацій і однакові назви стовпців;
- `null` у сховищі та експортері.

Файл `data/stock.csv` має 8 фізичних рядків, відновлено 6 об'єктів.

## 16. Відповіді на контрольні питання

1. **Яку проблему розв'язує параметр типу в Repository<T>?** Одне сховище працює з різними типами, а компілятор перевіряє їх без приведень.
2. **Чим параметризований клас відрізняється від raw type?** Raw type не перевіряє тип елементів, і помилка виявляється лише під час виконання.
3. **Навіщо Predicate<? super T> у методі пошуку?** Щоб приймати умову для `T` або його супертипу, наприклад `Predicate<Object>`.
4. **Чому all() має повертати незмінний знімок?** Щоб зовнішній код не змінив внутрішній список, а результат не змінювався після нових додавань.
5. **Що таке checked exception і коли він доречний у цій роботі?** Виняток, який потрібно обробити або оголосити. Він доречний для очікуваних помилок файлів і формату.
6. **Для чого зберігати cause власного винятку?** Щоб не втратити початкову технічну причину, наприклад `NumberFormatException`.
7. **Чим Path і Files кращі за складання шляху рядком?** Вони враховують роздільники ОС і дають готові операції з файлами.
8. **Чому кодування потрібно задавати і під час запису, і під час читання?** Інакше одна з операцій може взяти системне кодування і спотворити текст.
9. **Що роблять @Retention(RUNTIME) і @Target(FIELD)?** Перша зберігає анотацію під час виконання, друга дозволяє ставити її лише на поля.
10. **Чому анотація не виконує експорт сама?** Вона містить лише метадані, які читає експортер.
11. **Чим getDeclaredFields() відрізняється від отримання публічних полів?** Повертає всі поля, оголошені саме в цьому класі, зокрема приватні, але без успадкованих; `getFields` повертає публічні разом з успадкованими.
12. **Навіщо перевіряти trySetAccessible()?** Доступ може бути заборонено, і тоді потрібна зрозуміла помилка.
13. **Чому порядок полів для CSV потрібно зробити детермінованим?** JVM не гарантує порядок полів, а заголовок і значення мають збігатися.
14. **Чому split(",") не підходить для загального CSV?** Він розділить кому всередині лапок і не розуміє багаторядкових полів.
15. **Як екрануються кома, лапка й перенесення рядка в CSV?** Поле береться в лапки, а внутрішня лапка подвоюється.
16. **Чому порожній список потребує окремого параметра Class<T>?** Через стирання типів зі списку не можна дізнатися клас, потрібний для заголовка.
17. **Чим універсальний експортер відрізняється від предметного fromCsv?** Експортер працює з будь-яким анотованим класом, а відновлення знає типи й правила конкретного запису.
18. **Які рівні помилок розрізняє програма?** Модель, формат, значення, файл і рефлексія.
19. **Що доводить тест round-trip?** Що після запису й читання всі поля, їхні значення та порядок записів збереглися.
20. **Чому виняток не можна поглинати порожнім catch?** Помилка зникне, і програма продовжить роботу з неповними даними.

## 17. Висновки

Програма отримала `Repository<T>`, власний виняток, анотацію `@CsvColumn`, універсальний експортер і парсер CSV. Round-trip зберігає всі поля, зокрема тексти з комами, лапками та перенесеннями. Усі тести (131) проходять, SpotBugs не має зауважень, попередні режими працюють без змін.

Створений CSV із заголовком у UTF-8 стане вхідним файлом для наступного програмного блоку.
