## 4. Клас-сутність

Клас `SparePart` оголошено як `final`. Усі поля мають модифікатори `private final`, сеттерів немає, тому стан не змінюється після створення об'єкта.

| Поле | Тип | Інваріант |
|---|---|---|
| sku | String | не `null` і не порожній |
| name | String | не `null` і не порожня |
| stock | int | не від'ємний |
| unitPrice | double | скінченна і не від'ємна |
| supplier | String | не `null` і не порожній |

Для читання передбачено методи `getSku`, `getName`, `getStock`, `getUnitPrice` і `getSupplier`. Метод `toString` форматує ціну з `Locale.ROOT`, тому десятковим роздільником завжди є крапка.

Лістинг 1 – конструктор `SparePart`:

```java
public SparePart(String sku, String name, int stock, double unitPrice, String supplier) {
    requireFilled(sku, name, supplier);
    if (!Double.isFinite(unitPrice)) {
        throw new IllegalArgumentException("ціна має бути скінченним числом");
    }
    if (unitPrice < 0 || stock < 0) {
        throw new IllegalArgumentException("ціна та кількість не можуть бути від'ємними");
    }
    this.sku = sku;
    this.name = name;
    this.stock = stock;
    this.unitPrice = unitPrice;
    this.supplier = supplier;
}
```

## 5. Фабричний метод і record

`SparePart.fromCsv` приймає рядок у форматі `sku;name;stock;unitPrice;supplier`, перевіряє, що рядок не порожній і має п'ять полів, перетворює числа та викликає конструктор. Виняток `NumberFormatException` зберігається як причина нового винятку.

Правило непорожніх текстових полів визначено один раз у методі `requireFilled`. Фабрика викликає його до розбору чисел, щоб для рядка з кількома помилками причина була такою самою, як у лабораторній роботі №1.

Лістинг 2 – розбір чисел у `SparePart.fromCsv`:

```java
requireFilled(sku, name, supplier);

final int stock;
final double unitPrice;
try {
    stock = Integer.parseInt(fields[2].trim());
    unitPrice = Double.parseDouble(fields[3].trim());
} catch (NumberFormatException exception) {
    throw new IllegalArgumentException("ціна та кількість мають бути числами", exception);
}
return new SparePart(sku, name, stock, unitPrice, supplier);
```

Record `StockValue` об'єднує загальну кількість одиниць і вартість запасу. Його компактний конструктор відхиляє від'ємні та нескінченні значення.

Лістинг 3 – record `StockValue`:

```java
public record StockValue(long totalStock, double totalValue) {
    public StockValue {
        if (totalStock < 0) {
            throw new IllegalArgumentException("Загальна кількість на складі не може бути від'ємною.");
        }
        if (!Double.isFinite(totalValue) || totalValue < 0) {
            throw new IllegalArgumentException("Загальна вартість має бути скінченним невід'ємним числом.");
        }
    }
}
```

## 6. Тестування

Виконано 30 тестів: 14 у `CsvParserTest` і 16 у `SparePartTest`. Усі 13 тестів лабораторної роботи №1 збережено. У них змінено лише тип об'єкта та методи читання, очікувані значення ті самі.

Позитивні випадки:

- створення деталі через конструктор і `fromCsv`;
- обрізання пробілів навколо полів CSV;
- обчислення всіх показників і `StockValue` для кількох деталей;
- доступ до компонентів, `equals` і `hashCode` record.

Граничні випадки:

- нульова ціна й нульовий залишок;
- нульові підсумки `StockValue`;
- форматування ціни за німецької локалі.

Негативні випадки:

- `null` і порожні текстові поля;
- від'ємні значення, `NaN` і нескінченність;
- порожній рядок, чотири та шість полів, нечислові значення;
- точний текст причини для кожного виду помилки;
- порядок перевірок для рядка з двома помилками;
- хибні записи не змінюють статистику.

## 11. Відповіді на контрольні питання

1. **Яку проблему розв'язує клас-сутність порівняно з рядком і паралельними змінними?** Поля одного запису зібрано в одному об'єкті з іменами й типами, тому їх не можна переплутати за індексом, а правила перевірки зосереджено в одному місці.
2. **Що означають private і final у полях класу?** `private` забороняє доступ до поля ззовні класу, `final` дозволяє присвоїти значення лише один раз.
3. **Що таке інкапсуляція і яку проблему вона запобігає?** Це приховування стану за методами класу. Вона не дає зовнішньому коду перевести об'єкт у хибний стан.
4. **Чому перевірку інваріантів розміщують у конструкторі?** Через конструктор проходить кожен новий об'єкт, тому хибний об'єкт не може бути створений.
5. **Чим Objects.requireNonNull відрізняється від isBlank?** `requireNonNull` перевіряє, що посилання не `null`, а `isBlank` – що наявний рядок порожній або містить лише пробіли.
6. **Чому відсутність сеттерів може допомогти зберегти коректний стан?** Значення, перевірені в конструкторі, більше ніхто не змінить.
7. **Які методи й властивості автоматично отримує record?** Приватні `final`-поля, канонічний конструктор, методи доступу до компонентів, `equals`, `hashCode` і `toString`.
8. **Чим record відрізняється від звичайного класу-сутності?** Record прозоро подає набір значень, і його рівність визначають компоненти. Клас сам обирає, який стан приховати, які методи надати та як порівнювати об'єкти.
9. **Чому record не гарантує глибоку незмінність змінного списку?** `final` фіксує лише посилання. Сам список можна змінити, якщо не зробити копію, як `List.copyOf` у `ReadResult`.
10. **Для чого потрібен статичний фабричний метод fromCsv?** Він має зрозумілу назву й відокремлює розбір тексту від перевірки стану в конструкторі.
11. **Де потрібно перехоплювати помилку розбору одного рядка?** На рівні обробки рядка. У програмі це робить `CsvParser`, а `InventoryFileReader` додає номер рядка.
12. **Чому неправильний запис не можна додавати до списку до завершення перевірки?** Він потрапить у статистику та спотворить показники.
13. **Яке призначення toString і чому він не замінює формат CSV?** Він дає зрозуміле подання об'єкта для діагностики. Формат CSV має власні правила порядку полів і роздільників.
14. **Навіщо використовувати Locale.ROOT у toString і звіті?** Щоб числа виглядали однаково на всіх комп'ютерах.
15. **Що означає схема тесту AAA?** Arrange – підготувати дані, Act – виконати дію, Assert – перевірити результат.
16. **Які негативні випадки потрібно перевірити для конструктора?** `null`, порожні рядки, від'ємні ціну й залишок, `NaN` і нескінченність.
17. **Як довести, що рефакторинг не змінив зовнішню поведінку попередньої роботи?** Запустити старі тести та порівняти вивід двох версій на однакових даних.
18. **Чому тести попередньої роботи мають проходити після цієї роботи?** Вони описують поведінку, яку рефакторинг повинен зберегти.
19. **Які файли інфраструктури переносяться з попередньої роботи без повторного створення?** `pom.xml`, Maven Wrapper, `.gitignore`, `.gitattributes`, `.editorconfig` і файли ролей у `ai/`.
20. **Який рядок Вашої реалізації найкраще демонструє інкапсуляцію і чому?** `private final double unitPrice;` – ціну встановлює лише конструктор після перевірки, а читають її тільки через `getUnitPrice`.

## 12. Висновки

Запис про деталь перетворено на незмінний клас `SparePart`, який перевіряє стан у конструкторі й створюється з рядка CSV через `fromCsv`. Підсумки складу описано записом `StockValue`. Усі 30 тестів проходять, SpotBugs не має зауважень, а вивід програми збігається з лабораторною роботою №1.

У лабораторній роботі №3 `SparePart` стане базовим типом для `OriginalPart` і `ReplacementPart` із різним обчисленням гарантійної вартості.
