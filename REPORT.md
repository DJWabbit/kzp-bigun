## 4. Базовий тип

`SparePart` – абстрактний клас. Він містить спільні поля та перевіряє їхні інваріанти, тому підтипи цих правил не повторюють.

| Поле | Тип | Інваріант |
|---|---|---|
| kind | PartKind | не `null` |
| sku | String | не `null` і не порожній |
| name | String | не `null` і не порожня |
| stock | int | не від'ємний |
| unitPrice | double | скінченна і не від'ємна |
| supplier | String | не `null` і не порожній |

Абстрактний метод `warrantyCost` реалізують підтипи. Методи читання, `equals` і `hashCode` оголошено `final`.

**Чому спадкування.** Оригінальна деталь і замінник є різновидами деталі, мають спільний стан і відрізняються лише поведінкою. Інтерфейс не зберігав би спільних полів. Композиція підійшла б, якби деталь лише містила правило гарантії, але тут вид визначає саму деталь.

Лістинг 1 – конструктори `SparePart`:

```java
protected SparePart(PartKind kind, String sku, String name, int stock, double unitPrice, String supplier) {
    // Перевірка завершується до створення об'єкта, тому частково створеного стану не буває.
    this(requireValid(kind, sku, name, stock, unitPrice, supplier),
            kind, sku, name, stock, unitPrice, supplier);
}
```

## 5. Підтипи

| Підтип | Правило артикула | Гарантійна вартість |
|---|---|---|
| `OriginalPart` | без суфікса `-R` | 5% ціни × кількість |
| `ReplacementPart` | із суфіксом `-R` | max(3% ціни; 20 грн) × кількість |

Лістинг 2 – гарантійна вартість у `OriginalPart`:

```java
@Override
public double warrantyCost() {
    return getUnitPrice() * 0.05 * getStock();
}
```

Лістинг 3 – гарантійна вартість у `ReplacementPart`:

```java
@Override
public double warrantyCost() {
    double perUnit = Math.max(getUnitPrice() * 0.03, 20.0);
    return perUnit * getStock();
}
```

## 6. enum

`PartKind` має значення `ORIGINAL` («оригінальна») і `REPLACEMENT` («замінник»). Він зберігає підпис для звіту, визначає вид за артикулом і створює відповідний підтип без `switch`: кожна константа має власну реалізацію `create`.

Лістинг 4 – визначення виду за артикулом:

```java
public static PartKind fromSku(String sku) {
    if (sku != null && sku.trim().endsWith("-R")) {
        return REPLACEMENT;
    }
    return ORIGINAL;
}
```

`SparePart.fromCsv` викликає `PartKind.fromSku(sku).create(...)`. Формат рядка `sku;name;stock;unitPrice;supplier` не змінився.

## 7. equals і hashCode

Дві деталі рівні, якщо мають той самий підтип і артикул. Артикул однозначно позначає деталь, а залишок і ціна можуть різнитися. `getClass` не допускає рівності різних підтипів. Поля незмінні, тому хеш-код об'єкта в колекції не змінюється.

Перевірено: два рівні об'єкти мають однаковий `hashCode`, `HashSet` зберігає один запис, `HashMap` знаходить значення за рівним ключем, об'єкти з різними артикулами або підтипами нерівні.

## 8. Поліморфізм

`WarrantyReport` обробляє `List<SparePart>` і не перевіряє підтип. Реалізацію `warrantyCost` обирає Java за фактичним об'єктом. Щоб додати новий вид деталі, потрібні новий підтип, константа `PartKind` і правило її розпізнавання; звіт не змінюється.

Лістинг 5 – поліморфний цикл у `WarrantyReport`:

```java
for (SparePart item : items) {
    // Реалізацію warrantyCost обирає фактичний підтип.
    double cost = item.warrantyCost();
    total += cost;
    report.append(String.format(Locale.ROOT, "- %s (%s): %.2f%n",
            item.getSku(), item.getKind().getLabel(), cost));
}
```

Вивід `--warranty` після звичайного звіту:

```text
Гарантійна вартість
- BRK-001 (оригінальна): 750.30
- FLT-014-R (замінник): 500.00
- SPK-210 (оригінальна): 371.50
- TIM-008 (оригінальна): 735.00
Разом: 2356.80
```

## 9. Тестування

Виконано 51 тест: 14 у `CsvParserTest`, 16 у `SparePartTest` і 21 новий у `PartHierarchyTest`. Усі 30 тестів лабораторної роботи №2 збережено. У них лише `new SparePart` замінено на `new OriginalPart`, бо об'єкт абстрактного класу створити не можна; очікувані значення ті самі.

Позитивні випадки:

- створення обох підтипів, через `PartKind` і з рядка CSV;
- різна вартість через змінну базового типу;
- рівність у `HashSet` і `HashMap`;
- звіт про гарантію та його сума.

Граничні випадки:

- нульові ціна й кількість;
- межа між 20 грн і 3% ціни;
- артикули `-R`, `-r`, із `-R` усередині та з пробілами;
- порожній список деталей.

Негативні випадки:

- спільні інваріанти для кожного підтипу;
- артикул, що не відповідає підтипу;
- нерівність різних підтипів і артикулів.

## 13. Академічна доброчесність

Під час роботи використано Claude Code.

**Основа роботи.** Базою ієрархії стала модель `SparePart` і `StockValue` з лабораторної роботи №2; внесок у неї описано у звіті до тієї роботи.

**Внесок автора.** Автор визначив порядок роботи за етапами, рівень і вимогу сумісності CSV, розглянув і затвердив план. Автор спроєктував і написав реалізацію `PartKind`, логіку розпізнавання суфікса `-R`, валідацію підтипів та методи `warrantyCost`. Публікацію здійснено лише після погодження автором. Автор відповідає за код та зміст звіту.

**Внесок Claude Code.** Запропонував план, зокрема ознаку `-R`, формули гарантійної вартості та ключ `--warranty`. Інтегрував код автора в проєкт, перебудував `SparePart` на абстрактний клас, реалізував рівність, `WarrantyReport` і `--warranty`, дописав тести та Javadoc, порівняв вивід JAR двох робіт, підготував README і тексти звіту, зокрема чернетки відповідей на контрольні питання.

**Ролі.** У каталозі `ai/` описано ролі Менеджера, DevOps, Розробника, Валідатора, Документатора й Рецензента.

**Запити.** Скласти план ієрархії із сумісним CSV; перевірити та інтегрувати код автора; реалізувати решту затвердженого плану; перевірити тести, SpotBugs і вивід JAR.

**Прийняті рекомендації:** ознака підтипу в артикулі; рівність за підтипом і артикулом; окремий ключ `--warranty`; завершення перевірок до створення об'єкта.

**Відхилені пропозиції:** у плані артикул, що складається лише з `-R`, мав лишатися оригінальною деталлю; у реалізації автора він вважається замінником.

**Виправлені помилки:** SpotBugs виявив зайві перевірки `null` у конструкторах підтипів і виняток у конструкторі абстрактного класу; після виправлення зауважень немає.

Результати перевірено командами Maven, тестами JUnit 5, SpotBugs і запуском JAR. Автор може пояснити ієрархію, `PartKind`, `warrantyCost` та `equals`/`hashCode`.

## 14. Відповіді на контрольні питання

1. **Яку спільну проблему розв'язує базовий тип у предметній області?** Зберігає спільні поля й правила в одному місці та дає змогу однаково працювати з різними видами деталей.
2. **Чим відрізняються extends і implements?** `extends` успадковує один клас разом зі станом і реалізацією, `implements` зобов'язує клас виконати контракт одного або кількох інтерфейсів.
3. **Навіщо базовий клас може бути abstract?** Щоб не створювати «деталь узагалі» та вимагати від підтипів реалізації `warrantyCost`.
4. **Яку роль виконує виклик super(...) у конструкторі підтипу?** Ініціалізує та перевіряє спільну частину об'єкта до власних перевірок підтипу.
5. **Що перевіряє анотація @Override?** Що метод справді перевизначає метод базового типу з тією самою сигнатурою.
6. **Що таке поліморфізм і як він усуває розгалуження за типом?** Виклик через базовий тип виконує реалізацію фактичного об'єкта, тому перевіряти підтип через `if` не потрібно.
7. **Коли краще використати інтерфейс, а коли абстрактний клас?** Інтерфейс – для спільної можливості різних класів, абстрактний клас – коли є спільні стан і код.
8. **Що означає відношення «є різновидом» і чим воно відрізняється від композиції?** Замінник є різновидом деталі. За композиції один об'єкт лише містить інший, як звіт містить список деталей.
9. **Для чого використовують enum із полями та методами?** Для фіксованого набору значень, які мають дані й поведінку, як підпис і створення підтипу в `PartKind`.
10. **Чому значення enum можна порівнювати через ==?** Кожна константа існує в одному екземплярі.
11. **Які правила має виконувати пара equals/hashCode?** Рівні об'єкти мають однаковий хеш-код; `equals` рефлексивний, симетричний, транзитивний, узгоджений і повертає `false` для `null`.
12. **Чому змінне поле небезпечне для об'єкта, який є ключем HashMap?** Після зміни хеш-код стане іншим, і значення не знайдеться.
13. **Чому два об'єкти різних підтипів можуть бути нерівними за однакової назви?** Вони мають різну поведінку, а `equals` порівнює також `getClass`.
14. **Як поліморфна колекція обробляє об'єкти різних підтипів?** Цикл викликає метод базового типу, а Java обирає реалізацію підтипу.
15. **Які тести доводять, що підтипи мають різну поведінку?** `subtypesCalculateWarrantyDifferentlyThroughBaseType` порівнює вартість за однакових ціни та кількості.
16. **Які тести доводять коректність рівності в HashSet?** `equalPartsHaveOneSetEntry` перевіряє `equals`, `hashCode` і розмір множини.
17. **Що контролює sealed і навіщо потрібен permits?** `sealed` обмежує перелік підтипів, а `permits` називає дозволені.
18. **Чому switch за підтипами не повинен дублювати поліморфні методи?** Та сама логіка опиниться у двох місцях і може розійтися.
19. **Які попередні тести та результати потрібно зберегти після перебудови?** Усі 30 тестів лабораторної роботи №2 та її контрольний звіт.
20. **Яке рішення у Вашій ієрархії найкраще демонструє перевагу поліморфізму?** Виклик `item.warrantyCost()` у `WarrantyReport`: звіт не змінюється, коли з'являється новий підтип.

## 15. Висновки

`SparePart` став абстрактним базовим типом, від якого успадковано `OriginalPart` і `ReplacementPart` із різною гарантійною вартістю. `PartKind` визначає вид за артикулом і створює підтип. Реалізовано узгоджені `equals` і `hashCode`. Усі тести (51) проходять, SpotBugs не має зауважень, звичайний звіт збігається з лабораторною роботою №2.

У лабораторній роботі №4 цикли буде замінено запитами Stream API до колекції `List<SparePart>`.
